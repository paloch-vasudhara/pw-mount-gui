ADS-B Integration Findings

2026-11-07 · source: C:\Users\soar\Desktop\DELV\sip-aero-python (revision reviewed-python-client-20261107). This is a read-only review: nothing was run, and no connection was made. Goal: show aircraft on the Sky Viewer (hover + info) and cue the mount in aircraft mode, before Phase 6.

0 Summary

  • The package is a client kit, not the aircraft server. It holds:
    • one Python receiver (receive_ws.py, ~290 lines, one dependency websockets==17.4) and its tests;
    • the public server CA;
    • the contract documents for the SIP AERO platform at 10.22.123.68.
  • How we connect: WSS at wss://10.22.123.68/api/v1/ws.
    • Authentication is a revocable read token, sent as the first WebSocket message.
    • TLS is strict, checked against the bundled private CA.
    • REST history is at /api/v1/records. MQTT/TLS on port 8883 needs separate credentials.
  • The aircraft data is the decoded event kind (schema sip.aero.adsb.decoded.v1, DF17 only). It carries:
    • identification (callsign);
    • airborne position: altitude + CPR codes (Compact Position Reporting, ADS-B's encoded position format);
    • airborne velocity: ground speed, track, vertical rate, GNSS−baro difference;
    • target state.
  • Biggest finding: the platform does not provide latitude/longitude.
    • latitude_deg and longitude_deg are always null (position_status: needs_CPR_pair_or_valid_reference).
    • We have to decode CPR ourselves, from an even/odd message pair or against a known reference position.
    • It is a small, well-defined algorithm (~100 lines) that we can test against published vectors.
  • Accuracy is limited by delay, not by ADS-B precision.
    • The field of view is about 3°. One second of delay we don't correct for, on a 250 m/s aircraft 10 km away, moves it 1.4°.
    • So each position must be projected forward from its timestamp using the reported velocity.
    • The mount PC clock must be NTP-synced.
  • Mount cueing reuses our custom alt/az path engine (P21/P22): it sends PWI4 a short predicted path and refreshes it on every update.
    • Typical aircraft rates are 1–4°/s, within the mount's limits.
    • Overhead passes that peak above about 82° elevation exceed the 10°/s azimuth limit. They need the same near-zenith handling as satellites (Q18).
  • Four facts are unknown, and a short real capture from you settles them: the CPR field names, whether decoded publishing is switched on, the real feed delay, and where the receiver is. See Needed from you.
  • Recommendation: build it as Phase 5b (aircraft), before T6. T6's security, packaging and acceptance work then covers the new incoming feed.

Envelope
  • icao (6 hex);
  • timestamp + timestamp_status + timestamp_source (1 = receiver GNSS … 7 = holdover);
  • received_at;
  • crc_valid / frame_basis, and raw (28 hex when CRC-checked);
  • signal_raw, channel, message_id.
Identity, timing, quality
  • The platform doesn't decode surface positions (TC 5–8). We don't need them: we only cue airborne targets above Lim EL.
  • Missing values stay null, never zero.
  • No position-integrity fields (NIC/NACp) are exposed. The position message's TC gives only a rough integrity level.

WebSocket protocol

  • Packet types:
    • hello: a runtime snapshot that includes active-aircraft summaries, but not positions;
    • event;
    • gap;
    • heartbeat: about every 15 s when idle.
  • Each client has a 256-packet queue. On overflow the server clears it and sends a gap.
  • The server can't filter by ICAO or area, so we filter on our side.
  • Catch-up (after_id) and history paging matter for a client that must log every message. For live cueing, old positions are useless. We only stream forward: on a gap we resume live and skip what was missed.

4 What we can reuse

    • the auth-first handshake and the hello check;
    • the packet loop;
    • close code 1008 → "token rejected", treated as fatal with no retry loop;

    • the TLS error text that includes the verify code.
  • Not reused: the JSONL output, the stdin token prompt, and the full REST catch-up loop, since a live cueing feed drops history.

  • Validation: turn decoded_payload.schema.json into a pydantic model on the gateway. It rejects out-of-range values, unknown schema strings and oversized packets.
  • Test pattern: their mocked-socket tests become our fake platform, a local WS server replaying a recorded JSONL file. Automated tests never connect to the real platform (the same rule as for astrometry.net).

5 Data pipeline (proposed)

Everything runs in the gateway, for two reasons: the token never reaches the browser, and cueing needs the data next to the mount executor. The analysis service is not involved.

CPR position decoding

  • First fix (global decode): one even and one odd airborne position from the same aircraft, within 10 s of each other, give an unambiguous lat/lon.
    • Both frames must fall in the same longitude zone (NL); otherwise we wait for the next pair.
  • Later fixes (local decode): each new frame is decoded against that aircraft's own last position.
    • This is valid within 180 NM, with airborne precision of about 5 m.
  • Sanity checks: reject a position farther from the receiver than the range limit (≤ 350 km), or one implying more than ~1 000 kt since the last fix. After a rejection, start again from a fresh even/odd pair.
  • Implementation: our own code (~100 lines), tested on the published worked example from The 1090 MHz Riddle (ICAO 40621D even/odd → 52.2572°, 3.9194°).
    • The common library, pyModeS, is GPL-3.0, which conflicts with packaging (Q38).

Altitude

  • Barometric altitude (TC 9–18) is pressure altitude, referenced to 1013.25 hPa. Depending on the weather it can differ from the true height by several hundred metres.
  • Use the best source available, in this order:
    1. GNSS height (TC 20–22);
    2. baro altitude + the latest gnss_minus_baro_altitude_ft from TC19, if no more than 60 s old;
    3. baro altitude alone, flagged "baro" on the card.
  • For scale: 100 m of height error is 0.57° at 10 km and 0.29° at 20 km.

Time base & latency

  • Time of each fix: the payload timestamp when timestamp_status ≠ 0 and the source is GNSS or NTP (codes 1, 3, 4). Otherwise received_at (the server's receive time), flagged as lower quality.
  • Delay measurement: the gateway measures now − fix time for every message.
    • The median and 95th-percentile delay appear in the ADS-B status.
    • The predictor always projects to the actual time the command is sent.
  • The mount PC clock must be NTP-synced. A clock error becomes an along-track error: 0.5 s ≈ 0.7° at 10 km.

Az/El geometry

  • WGS84 lat/lon/height → Earth-centred coordinates (ECEF) → local east/north/up (ENU) at the Settings site → azimuth, elevation and slant range.
  • This includes Earth's curvature, so distant aircraft need no extra correction.
  • Refraction: the astronomical model we use for stars and satellites doesn't apply to targets inside the atmosphere. The bending for aircraft is about 0.03° at 50 km, negligible against the 3° FOV. So the path gets geometric alt/az (note under Q39).

Prediction

  • First build: project forward from the last fix at the reported velocity (east/north knots plus vertical rate), on a flat local plane.
    • When the aircraft is turning, its last 2–3 track values give a turn rate, and the projection follows the turn.
  • The H3 Kalman predictor (in the logic sheet as "planned") comes later. We add it only if the measured gap between predicted and next real fix, on real tracks, exceeds the budget.

7 Mount cueing (aircraft mode)

  1. Track request from the card or the AIRCRAFT tab:
    • run the checks (see safety rules);
    • slew to where the aircraft will be when the slew finishes (the T4.2 rendezvous logic, with the aircraft predictor in place of sgp4).
  2. Following: on every new fix (about 2 Hz for position and velocity, throttled to 1 Hz):
    • build a new predicted path from now − 0.5 s to now + 10 s, with a point every 0.5 s;
    • replace the running path (new + add + apply, update_wrap=0);
    • set the wrap window to cover the predicted route (P21).
  3. Gaps in the feed: the mount keeps following the last path, which covers up to 10 s ahead. If no fresh fix arrives for 5 s, the mount stops (Q45).
  4. End: any of these ends the track and leaves the mount STOPPED, with the reason on the card, as for satellite tracks:
    • STOP;
    • the aircraft drops below Lim EL or goes out of range;
    • the Sun;
    • a rate limit;
    • the feed is lost.
Probe done (P23, 11-07, PWI4 Simulator). Replacing a running path every 1 s works: apply ≈ 0.06 s, no stop or jump, 0.023° mean / 0.17° max following error on a GA fly-by (2 s updates: 0.019° / 0.15°). With a 1 s feed delay, the velocity-based prediction held 0.18° mean through a 3°/s turn; without delay compensation the error was ≈ 2°. The first path point must be in the past (a future first point makes the mount pause: 0.14° mean). After the last point the mount holds still, so the gateway must STOP on feed loss. Overflights peaking at 82.5° and 86.3° followed at 0.015° mean on the sim, but the sim axis reached 36°/s, so the real zenith limit has to come from the L-350.

  • The only hard case is a near-zenith overflight, where the azimuth rate is speed ÷ the horizontal miss distance.
    • On the sim the axis saturated at 20.4°/s (P22). For a cruising aircraft that is a peak of about 86°.
  • Treatment, as for satellites:
    • allowed, with a "tracking lags near the zenith" note (Q18);
    • refused above a peak elevation still to be decided (Q46).

Safety rules (TRACK AIRCRAFT button + monitor)

  • Data: a fresh position (≤ 3 s old), a completed first CPR fix, and the aircraft airborne.
  • Lim EL: above Lim EL now, or predicted to cross it within the rendezvous window. The track stops when the aircraft drops below Lim EL (G3).
  • Sun: not within 15° of the Sun. If the predicted path enters the 16° circle, the track stops before it. Aircraft get no detour (Q45).
  • Range: within the range limit (from Settings or the tab's preset).
  • Unchanged:
    • the link-loss stop (G4) and the start-up stop;
    • one tracked object at a time (G5): an aircraft track replaces a satellite track, and the other way round.

9 Security

  • The token stays in Windows Credential Manager.
    • The gateway sends it only in the first WSS message.
    • It is never logged, audited or returned to the browser (the same rules as the astrometry key).
  • Strict TLS with the bundled CA:
    • its fingerprint is pinned in code and tests;
    • no proxy, and the hostname check stays on;
    • a TLS failure shows the verify reason and never falls back to an unverified connection.
  • The feed is untrusted input that can move the mount.
    • We validate it against the schema, cap sizes (the platform caps payloads at 32 KB; we cap packets too), check numeric ranges and apply the sanity checks.
    • Every safety rule still applies. A bad or spoofed position can at most point the mount at the wrong place, inside the safe limits.
    • ADS-B itself is an unauthenticated radio broadcast, which is why spoofing is possible.
  • Read-only use: we never call the admin or token routes, and never publish to MQTT.
  • T6.1 extends its fuzz testing to the feed parser.
